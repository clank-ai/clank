# Flows, step 10: a flow built with the model: implementation plan

> At the owner's request (2026-10-20, through the build's coordinator): "for starting the flow I need the ability to
> use the LLM to build the flow at the beginning, and then I want to let the flow go from there", with their three
> answers (design 0013 §15). As for the earlier plans, the files, interfaces and tests by name and intent; the code is
> in the commits.

**Goal:** [design 0013](../design/0013-flows.md) §15 and §14 step 10: `n` in the Flow view (`N` in VS Code) or `clank
flow new [NAME]` opens a planning session in the workspace's OpenCode window, here or in VS Code; the model reads the
folder, asks the owner, writes `BRIEF.md` with them and drafts the flow with `flow_draft`; Clank checks the draft,
answers its problems and warnings, and writes the flow's file; the owner is told "flow built: look, then r to run";
the built flow shows on F10 with its boxes, models and warnings; `r` starts it; it runs on its own until its final
review.

**Architecture:** A new part of the flows component, `building.py`: the planning (`Planning`, a JSON file of the
service's state beside the flow's runs, with its first message), its pure parts (a built flow's values over a draft,
its own rules, the first free name, the first message from `prompts/build.md`) and `Building`, built by the flows'
service beside the runner and the next flow: `open` (here: `agents/prepare` gives the window's command and port; in VS
Code: the window running, else the one VS Code's extension prepares, heard through a new hook of the agents'
`prepare`), the session started on that port by the bridge's `implement` (now with the planner and a wait for the
window, shown again twice) on a thread of its own, since the window starts after `prepare` answers; and `draft`, the
check and the write, the question asked through the next flow's channel. The runner gains one rule: a built flow's
first YOU box is done by its brief. The gateway's allowlist gains `POST /flows/draft`, Clank's MCP server
`flow_draft`. The Flow view follows a built flow, says so in Waiting for you with the warnings, and gains `n`, `N` and
`r` on a flow not run. `clank flow new` serves the command line.

**Tech stack:** Python 3.12, AnyIO, FastAPI, click, Textual, pytest; the runner's rig of plan s24, the fake bridge,
the fake OpenCode server of the bridge's tests.

**Spec:** [design 0013](../design/0013-flows.md) §2, §9, §10, §11, §12, §14 step 10 and §15 (2026-10-20); decisions
[0097](../decisions/0097-a-flow-is-built-by-talking-it-through.md),

## Global Constraints

- Nothing runs OpenCode, a container, Docker, a model, the service on its port or the gateway on its port: the fake
  bridge, the fake OpenCode server of the bridge's tests and synthetic folders only; nothing opens a window.
- No new dependency. Tests first, each test file's docstring naming the design sections it verifies, test names
  sentences.
- The bridge and Clank's MCP server change, so the sandbox image does (its tag is its folder's checksum).
- The owner is the sole author of every commit (no trailer). The generated files are regenerated by `uv run python -m
  tools.check --fix`; the console's snapshots with `CLANK_UPDATE_SNAPSHOTS=1`, each difference read.

## Claude's calls (2026-10-20)

Design 0013 §15 lists them (1-12); the decisions record why. In short: the session on the workspace's window, shown
with `/tui/select-session` (no CLI flag); here by `agents/prepare`, in VS Code by the window running or the one VS
Code's extension starts; `n` where the owner is (`TERM_PROGRAM`), `N` in VS Code; one planning per workspace, its name
given or `flow`, `flow-2`, ...; the planner's first message from `prompts/build.md`, kept; `flow_draft` scoped to the
planning open in the workspace, refused once the flow ran; Clank's settings over the draft's; a built flow's own rules;
its YOU done by the brief at each run; the next flow's question as the channel; the Flow view following a built flow;
three things left out. Four more, found while planning and from the owner's requirement for SSH:

13. **The planning's states:** `waiting` (for its window), `opening` (its session being started on the window's port),
    `talking` (its session started), `built` (a draft written; more may follow), `failed` (the window did not answer,
    or the bridge refused, said), `set aside` (a newer planning in the workspace) and `ran` (its flow's first run
    began: drafts refused from then on).
14. **The window's port** reaches a planning that waits through a hook of the agents' part (`Agents.on_prepared`, told
    each `prepare` with its workspace and port), so the agents never import the flows (decision 0019: no cycle).
15. **A draft's answer** is the service's words for the model: refused (409), "Not written. Fix each, then call
    flow_draft again:" and each problem with its field, then the warnings; written, "Written as <id> ..." with what
    Clank set, the warnings, and to tell the owner to look in the Flow view (F10, or `clank console --page monitor --view
    flow`), then press r.
16. **Over SSH** (the owner's requirement, 2026-10-20, through the coordinator: the first real test runs over SSH from
    a Linux PC into this Windows PC, the console in that SSH terminal): when `SSH_CONNECTION`, `SSH_CLIENT` or
    `SSH_TTY` is in the environment of the console or `clank flow new`, the planning opens in that terminal, whatever
    asked for VS Code, said so; the choice is the client's (`clank/kernel/where.py`, shared by the console and the
    command, since the kernel is the one place both may import). Nothing from `n` to `r` needs the PC's own screen.
    `clank console` gains `--view` (`--page monitor --view flow`), for a terminal that keeps F10 for itself.
