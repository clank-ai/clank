# M1.5: the console's runtime pages, VS Code, and the prototype's profiles: implementation plan

> As for M1.1-M1.4, this plan gives the files, interfaces and tests by name and intent; the code is in the commits,
> written test-first.

**Goal:** what M1 runs is seen and driven from the console and VS Code (design 0003 §8): the *Models* page (each slot:
what it runs, since when and why, the memory it took beside the GPU's, the last switches; load, switch, unload,
check), *Presets* (each preset with its fit now and its last start; switch to it, check it, show its file), *Providers
and models* (each engine's versions and where each is installed; each model's files and where they are on each host;
install by recipe, download), and *Launch options* (a preset's options, each with its value, where the value comes
from, the flag it maps to and what it does; the command line). VS Code's status bar shows the main slot, and *Clank:
Switch model* picks a preset. `clank import` writes a preset for each of the prototype's profiles.

**Architecture:** the pages belong to the runtime component (`component.console`, as the machine's and Docker's do),
under `clank/components/runtime/console/`; they read what they show from the API through the console's data (new
topics: `slots`, `presets`, `engines`, `launches`, kept current by the events that touch them) and ask for the rest
when shown (a preset's plan and options). Every action is an operation the service runs (design 0002 §2.4), so the
operations page follows it and the message line says how it went. A picker (a list over the page) chooses a preset or
an engine.

**Spec:** [design 0003](../design/0003-the-runtime.md) §7.4 and §8; design 0001 §3.5 (where a value comes from), §5.2-§5.3.

## Global Constraints

- Everything of M1.4's global constraints holds.
- The console holds nothing of its own and never calls the API on the screen's thread (design 0001 §5.1).
- Every key is in the keys bar or the help page, every action in the palette (Ctrl+P), `?` explains what has the focus.

## Review Focus

1. **A switch started from the console while another runs:** refused as busy, in the service's words, on the message
   line. Pinned in Task 2.
2. **A preset that cannot run** (not installed, files missing, does not fit): the presets page says why before
   anything starts. Pinned in Task 3.
3. **The service stops while a page is on screen:** the page says so and comes back when the service does (the
   console's own behavior, kept). Pinned in Task 2.
4. **A profile of the prototype's with an argument Clank's adapter does not know:** the preset is written with what
   maps, and the rest is said in its notes, never dropped silently. Pinned in Task 6.
5. **VS Code while no slot runs:** the status bar says what the slot is (stopped, failed and why). Pinned in Task 5.

---

### Task 1: The runtime's data for clients

**Files:** `clank/components/runtime/api.py`, `service.py`; `clank/console/data.py`; tests `test_runtime_api.py`,
`tests/console/test_data.py`.

**Interfaces:** `GET /runtime/launches?limit=N` (the newest launches); `GET /runtime/gpu` (the GPU's memory now);
`GET /runtime/presets/{name}/plan` (the command line, the memory estimate with its fit now, and each option with its
value, its source, the flags it maps to, its help and memory note); hosts kept by the runtime, so a WSL host's home is
read once. The console's topics `slots`, `presets`, `engines`, `launches`; an event `runtime.slot` touches `slots` and
`launches`, a preset's settings event `presets`, an install's or a download's end `engines`.

### Task 2: The Models page

**Files:** `clank/components/runtime/console/models.py`, `console/pick.py`, `component.py`; tests
`test_console_models.py`.

**Interfaces:** key 8; each slot: its status since when and why, its preset and model, the engine and host, port and
process; its memory: what it took and needed beside its estimate and the GPU's use now; the last switches. `l` loads a
preset picked from a list, `w` switches to one, `u` unloads, `c` checks the slot's preset (its items in a window).

### Task 3: The Presets page

**Files:** `console/presets.py`; tests `test_console_presets.py`.

**Interfaces:** key 9; each preset: title, engine and version, model, fit now (or why it cannot run), its last start
(when, how long, memory). Enter switches the main slot to it, `c` checks it, `v` shows its file, `o` opens its launch
options.

### Task 4: Providers and models; launch options

**Files:** `console/providers.py`, `console/options.py`; tests `test_console_providers.py`, `test_console_options.py`.

**Interfaces:** *Providers and models*, key 0: each engine with its versions, its installs (host, how, folder, detail)
and its recipes; each model with its files, and where each is on each host (a `model-file` record, else the host's
models folder). `i` installs an engine by its recipe on a host picked from a list; `d` downloads a model's file.
*Launch options*, key F2: the preset chosen on the presets page (else the main slot's): each option's value, source
(the preset, Clank's default, the engine's own), the flags it maps to and its help, then the command line and the
memory estimate; `e` opens the preset's file in the editor the system gives JSON files.

### Task 5: VS Code

**Files:** `vscode/src/core/state.ts`, `controller.ts`, `presenter.ts`, `extension.ts`, `package.json`; tests
`vscode/test/*.test.ts`.

**Interfaces:** the status bar's Clank item shows the main slot (`$(server) Clank · NInfer 44K fitted`, or its state
when nothing runs, the tooltip saying why); *Clank: Switch model* picks a preset (its fit or why it cannot run) and
switches the main slot; `runtime.slot` events keep it current.

### Task 6: the prototype's profiles

**Files:** `clank/components/runtime/importing.py`, `cli.py`; tests `test_import_prototype.py` with a synthetic
registry under `tests/fixtures/prototype/`.

**Interfaces:** `clank import REGISTRY [--dry-run]`: for each profile of the prototype's registry, a preset (id
`prototype-<profile>`) with the engine and model it maps to and the options its arguments set, read through the
adapter's own option maps; arguments that map to nothing are listed in the preset's notes; a preset that exists is
left as it is and said. It writes nothing else and leaves the registry as it is.

- [x] Tasks 1-6, each test-first, committed and pushed; CI green at the end (0cb4a90..a67a295).

## Rulings made while building

- **Task 2: the keys bar keeps the keys that act anywhere.** With *8 models* in it, *q quit* no longer fit at 120
  columns, and two more pages come; each menu entry already starts with its key, so the bar now shows F1, `?`, `q` and
  Ctrl+P, and a page's digit only beside it in the menu (and on the help page). If wrong, a page's keys are one more
  look away.
- **Task 2: the home page's models row shows the slots** (what each runs and its state, or why it runs nothing), as
  its red placeholder said M1 would.
- **Task 2: one picker for the shell** (`clank/console/pick.py`), since installs, downloads and presets all choose
  from a list; it only chooses, and the page acts on the choice.
- **Task 3: two bugs found and fixed on the way.** The presets list judged a preset's model against Clank's own
  catalog while launches used the runtime's (a test's catalog showed the difference); both use the runtime's now. And
  `v` on the home page (a question shown whole, M0) never showed anything: the window opened, then the same keystroke
  reached the window's own `v` (close) binding. A window a key opens now opens once that key is handled, and a key a
  page acts on closes only a window that was open before it; a test pins both.
- **Task 4: where a model's file is, only on the hosts that read it.** The page asks each host whose installed engine
  reads the file's format whether the file is there, and no other: asking a WSL distribution that does not run starts
  it. A file on another host shows when an engine reading it is installed there.
- **Task 4: key 0 sorts after 9** in the menu, as on the keyboard, and *Launch options* is F2 (the digits are taken).
- **Task 4: the console follows the hosts too** (a `hosts` topic), for the install's and the download's pickers.

## Final review

Self-review (no subagents), 2026-10-13, against the review focus: a load refused as busy is said on the message line
in the service's words (test_console_models); a preset that cannot run says why on the Presets page
(test_console_presets); the service stopping is the shell's own behavior, unchanged (the header says it, the pages
keep what they showed; test_data, test_shell); a profile's unknown argument is named in the preset's notes
(test_import_prototype); VS Code's tooltip says the slot's state and why when nothing runs (controller.test.ts). On this
machine, the prototype's seven profiles were imported (each mapped whole, but for three environment variables Clank's
launches do without), and the prototype's daily profile came out as Clank's own *daily 262K*.

Deferred minors:
- The Models page reads the GPU's memory every five seconds while it is on screen (an `nvidia-smi` run each time).
- The Providers page asks each host for each model file's size whenever an install, a download or a host changes.
- The picker has no filtering as one types; with many presets, the arrows are the way.
- `e` on one of Clank's own presets opens the file inside the installed package; the message line says to save a
  copy in config/presets instead, but nothing stops an edit there.
