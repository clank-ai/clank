# Flows, step 7: gates in VS Code and on the phone: implementation plan

> At the owner's request (2026-10-19): the new menu, the Monitor and flows (the model orchestrator) built as quickly as
> possible, with the same care as always. This is design 0013's seventh build step. As for the earlier plans, the
> files, interfaces and tests by name and intent; the code is in the commits.

**Goal:** [design 0013](../design/0013-flows.md) §14 step 7: a gate shows in VS Code with its answers, *edit* opens the
deliverable and *diff* the two tries in VS Code's diff; the phone lists a gate and a batch of proposals and answers
them; an answer from one client closes the question on the others (§10: "A gate is a question, answered once, from
any client").

**Architecture:** What a flow waits for is told by the service: `GET /api/v1/flows/waiting` lists each question a
flow's run waits for (a YOU box, a gate, a failed box, a box whose *when done* waits) with its flow, run and box, the
files it shows (each with its place in the folder, the box that wrote it and the tries that kept a copy of it), and the
answers that take words (`waiting.py`, `Flows.waiting`). A try's copy of a deliverable is read through
`GET /api/v1/flows/{workspace}/{name}/copy` (the run, box, try and file), from the try's folder only. In VS Code a new
part of the extension's core, `Gates` (`vscode/src/core/gates.ts`), takes every question about a flow from the
controller, as `Reviews` takes those about a change: it shows the gate as a notification with its answers and two
more buttons, **Open** (the file in the folder, the gate shown again once it is saved: *edit, then approve*) and
**Diff** (the last two tries' copies in VS Code's diff, the gate shown again); an answer that takes words asks for
them first. A gate settled elsewhere is never shown again, its diffs close, and a click on its notification still on
screen says who answered it instead of answering. The phone's overview gives each question about a flow its flow's
view; the page draws it under its flow with its files, reads a file it shows as it stands in the folder, and sends a
note with *send back* and *try again*.

**Tech stack:** Python 3.12, FastAPI, pytest; TypeScript and Node's own test runner for the extension's core; the
phone page's plain script (checked with `node --check`).

**Spec:** [design 0013](../design/0013-flows.md) §2, §8, §9, §10 and §14 step 7 (approved 2026-10-18); [design
0002](../design/0002-the-foundation.md) §2.5 (a question is answered once, from any client); [design
0005](../design/0005-the-phone.md) §4 (the phone: what waits) and [design 0007](../design/0007-reviewing-changes.md)
§6 (VS Code: questions as notifications, changes as diffs); decisions
[0061](../decisions/0061-the-runner-is-an-operation-per-box-in-the-service.md) (gates, YOU boxes and proposals are
questions) and [0064](../decisions/0064-the-model-changes-a-flow-only-by-proposals.md); what step 2 built ([plan
s24](s24-flows-the-runner.md), calls 8-12: the questions' options).

## Global Constraints

- Nothing here runs OpenCode, a container, Docker, a model, or VS Code itself: a GPU benchmark ran
  through them, and the extension's suite inside VS Code opens a window. The service's side is tested against the fake
  bridge and synthetic folders; the extension's core with Node's own runner and fakes; nothing opens a window.
- No new dependency. Tests first, each test file's docstring (or header comment) naming the design sections it
  verifies, test names sentences.
- The owner is the sole author of every commit (no trailer). Each task is one commit; the generated files are
  regenerated by `uv run python -m tools.check --fix`.

## Claude's calls (2026-10-20)

1. **One view of what a flow waits for, for every client.** The service says, for each question a flow's run waits for,
   its flow, run, box and kind, the files it shows and the answers that take words; VS Code and the phone draw it, so
   neither knows the runner's rules (which box wrote a file, which answers read words).
2. **The files a question shows:** a gate's (its `shows`, else the deliverable of the box before it that writes one, as
   the runner's gate says); a YOU box's own files to write; a failed VERIFY's, the deliverables of the box it checks
   (at its loop's gate, board D3: the plan's last two tries to diff, and *one more try*'s words for that box); another
   failed box's, and a box's whose *when done* waits, its own deliverables. Each names the box that wrote it and the
   tries of that box in the flow's run that kept a copy.
3. **The answers that take words** are *send back* (the note for the box's next try) and *try again* (words for its
   next try), as the runner reads them (plan s24, calls 9 and 10); every other answer is an option alone. The phone
   now sends them too: plan s24's call 9 had the phone send back without a note.
4. **Diff compares the last two tries that kept a copy** of the file (design 0013 §8: "`d` diffs two tries"); with
   only one try there is no Diff. The tries' texts come through the copy route, never from the disk, so a window on
   another machine of the tailnet works the same.
5. **Open opens the file in the folder**, as it stands: what the owner edits at a gate is what is approved (§8, §10).
   A file not written yet (a YOU box's) opens as a new file at its place, written there when saved.
6. **A gate comes back** in VS Code after Diff at once, after Open once that file is saved ("the owner approves once it
   is saved", §10), and after a note's box is left with Escape; a notification dismissed is not shown again, and the
   status bar's count and the Questions command still reach it. After the review: they reach it even while its first
   notification still waits unclicked, since VS Code moves such a notification to its notification center with its
   promise pending; no notification of a gate is kept off the screen for an earlier one, and the first clicked answers
   it (task 9).
7. **VS Code cannot close a notification** (its API has no way to), so a gate answered elsewhere is closed as far as
   VS Code allows: it leaves the count and the Questions list, is never shown again (not after a save either), its
   diffs close, and a click on its notification still on screen says who answered it, from the service's event,
   instead of answering.
8. **A batch of proposals is a question about its flow** (design 0013 §6, decision 0061), asked by step 4 with
   accepting and rejecting them all among its options (§9: "The phone may accept or reject them all"). The phone and
   VS Code show any question about a flow under its flow with its options, whether or not a run's file names it, so the
   batch shows once step 4 asks it; this step's test asks one directly in that shape, standing in for step 4's.
9. **The phone reads a file a question shows** as it stands in the folder now (what an approval takes), by the
   question and the file's place in its list, never by a path the phone sends, up to the flow's `whole_up_to` (the
   size a first message hands whole); a larger or binary file is said so, by its size.
10. **A run's file is written while a client reads it** (found by task 6's tests): the phone and VS Code read the
    runs' files from their own threads while the runner writes them, and Windows refuses to replace a file that is open
    for reading at that moment ("Access is denied"), which failed the box being started. `Runs.save` waits for the read
    to end, trying again for up to about a second, rather than failing.

## Review Focus

1. **The copy route and the phone's file route** read only inside a try's folder, and only the files a waiting
   question shows: no path a client sends leaves them.
2. **A gate settled elsewhere** is never answered again from VS Code (the stale notification, the saved file).
3. **The words of an answer** reach the box's next first message from the phone and from VS Code.
