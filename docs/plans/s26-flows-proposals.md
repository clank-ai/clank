# Flows, step 4: DECOMPOSE's proposals: implementation plan

> At the owner's request (2026-10-19): the new menu, the Monitor and flows (the model orchestrator) built as quickly as
> possible, with the same care as always. This is design 0013's fourth build step. As for the earlier plans, the files,
> interfaces and tests by name and intent; the code is in the commits.

**Goal:** [design 0013](../design/0013-flows.md) §14 step 4: a box's model reads its flow and proposes boxes with
`flow_read`, `flow_propose_box` and `flow_submit` (Clank's MCP server, through the gateway's `/flows/` routes, to the
service); each proposal is checked when staged and refused with its reason; proposals gather in a batch in the run's
folder and wait for the owner, who accepts, edits then accepts, or rejects each, or accepts all (from the command line
first); auto-accept, within its cap, lets them join at once; accepted boxes join the flow's file, marked with the run
and the box that proposed them; a DECOMPOSE run again replaces only its tasks that have not started; the planner may
use the tools. INTEGRATE's first message names every deliverable before it (§2: "a summary of every deliverable").

**Architecture:** A batch is a JSON file beside the proposing try, `run-<n>/<box>/try-<k>/proposals.json`
(`proposals.py`: `Batch`, `Proposal`, `Batches`), each proposal holding the box as it would join the flow. Joining is
a pure function of the flow's values (`proposals.joined`): it puts the accepted boxes in and rewires the lines (a
DECOMPOSE's tasks fan out from it and join at the box after it, §3), and the flow's own rules then check the result,
so a proposal that would break one is refused in the rule's words. The service's side (`proposing.py`: `Proposing`,
used by the runner) gives a proposal to the box at work in the workspace that sends it (one box at a time, §6, §9),
as a verdict is given; asks the owner one question about a batch when it is submitted; decides proposals (the owner's
command, the question's answer, or auto-accept), writing the flow's file through the settings like any change, so an
edit made on the version it replaced is refused with both versions shown (design 0002 §2.2). The driver holds a run at
a box whose proposals still wait (a `Waiting` of kind `proposals`), decided from the run's and the batch's files, so a
restart goes on the same way. The gateway forwards reading, proposing and submitting as the client `agent`, and
nothing that decides.

**Tech stack:** Python 3.12, AnyIO, FastAPI, click, pytest; the fake bridge and the runner's rig of plan s24.

**Spec:** [design 0013](../design/0013-flows.md) §2, §3, §6, §9, §10 and §14 step 4 (approved 2026-10-18); decisions
[0057](../decisions/0057-a-flow-is-a-chain-of-boxes.md),
[0061](../decisions/0061-the-runner-is-an-operation-per-box-in-the-service.md),
[0064](../decisions/0064-the-model-changes-a-flow-only-by-proposals.md),
[0066](../decisions/0066-a-flow-is-a-settings-file-in-clanks-home.md) and
[0020](../decisions/0020-enforce-where-it-can-be-stopped.md); what steps 2, 3 and 7 built ([plan

## Claude's calls (2026-10-20)

1. **Whose proposal.** A proposal goes to the box at work in the workspace its MCP server names (one box runs at a
   time, §6; the server knows its workspace, not its session, §9), while its try runs: its first message sent, its
   end not yet collected, as a verdict (plan s25, call 1). Any box a model runs may propose. Otherwise it is refused
   with why (409), in words the model can act on. A `flow` named while a box works must be that box's flow.
   *Left for later:* a proposal from the workspace's own agent with no box at work (§9: "the proposal names its flow
   and comes from the workspace's agent"): it has no run to keep its batch in, and its mark (`proposed.run`,
   `proposed.by`) needs another shape; until then it is refused, saying that only a box of a running flow proposes.
2. **The batch** is one per try of the proposing box, in that try's folder. Its proposals are numbered in the order
   proposed, and each takes its id in the flow when staged: `T<n>` for a TASK (`P`, `V`, `D`, `I`, `G`, `Y` and a
   number for the other types), the lowest number that no box of the flow and no proposal of the run takes. An id is
   never reused for another proposal in a run, so the run's file never mixes two boxes' tries.
3. **Where a proposal goes** (`after`, a box of the flow's file, not a proposal). Several after one box run in the
   order proposed, whatever order they are accepted in. A TASK after a DECOMPOSE, or after one of its tasks, joins the
   DECOMPOSE's tasks (they fan out from it and join at the box after them, §3); any other box goes between its box and
   the box after it. A VERIFY proposed after a box checks that box, its fail line back to it (the tool names no
   `checks`). Whatever does not keep §3's rules then is refused in the rule's words.
4. **The checks**, in order, each refusal naming the argument: the type (one of §2's, in any case); `after`; the
   title and the prompt not empty; a deliverable for every type but VERIFY, DECOMPOSE and GATE; each deliverable in
   the folder, and none in a folder agents load their settings from (`plans.SETTINGS`) nor an instructions file
   (`plans.INSTRUCTIONS`), in any case; each file it sees in the folder; the mode; the preset, for the main slot; then
   the flow, with the batch's proposals still waiting and this one joined, keeps §3's rules. An edited proposal is
   checked again the same way.
5. **Submitting asks one question** about the batch, about its flow: *accept all* (a) and *reject all* (r), its
   detail each proposal still waiting (its place, type, id, title, deliverable and model) and its why; the phone and VS
   Code show it with those options (plan s29, call 8). `flow_submit` with nothing proposed is refused. Each proposal can
   also be decided alone, from the command line or the API (accept, edit then accept, reject); when the last is
   decided, the question is withdrawn, saying so. An answer to it decides every proposal still waiting then.
6. **The run waits for the proposals.** A DECOMPOSE is done only when its session ended after submitting at least one
   proposal (§2), else it fails ("it ended without submitting its tasks") and waits at a gate. A box done whose last
   try has proposals still waiting holds the run there (`Waiting` of kind `proposals`) until each is decided, then
   goes on along the flow as it is then: the tasks accepted come next. Proposals staged but never submitted are asked
   about when their box is done (its end submits them). At a failed DECOMPOSE's gate, *take it as it is* asks about
   what it staged; *try again* and *skip the box* set it aside.
7. **Accepted boxes join the flow's file at once**, written through the settings like any change (by the owner, or by
   `clank (auto-accept)`), each marked `{run, by, accepted}` (decision 0064); a write refused (the flow changed
   meanwhile and no longer takes the box) leaves the proposal waiting, saying why. A flow's run reads its file as it
   is, so the tasks accepted run in this run, one at a time, each handed the deliverables of those before it (§3).
8. **Auto-accept** counts per run: a proposal that passes the checks joins at once while fewer than the flow's cap
   joined by auto-accept in the run; past it, it waits for the owner.
9. **A box run again proposes anew.** A box's new try sets aside the proposals of its earlier tries still waiting
   (*replaced*, their question withdrawn). The first proposal of a try to join takes out of the flow the boxes that box
   added before (`proposed.by`) that have not started in this run (no try), reconnecting the lines around them;
   those that ran stay (and run again as running from a box says). The batch keeps which it took out.
10. **The agent never decides.** The gateway forwards `GET /flows/read`, `POST /flows/propose`, `POST /flows/submit`
    and `POST /flows/verdict` only; the service's routes that decide refuse the client `agent` (403), and the runner
    refuses a decision whose actor is a session.
11. **`flow_read`** answers JSON: the flow, the box at work (the reader's own), each box in the order they run with
    its type, title, state in the run, tries, deliverables and the boxes after it, and the run's proposals with their
    states. With no box at work, `flow` names the flow (its boxes, no run); without it, the workspace's flows are
    listed. It is marked read-only.
12. **A nudge never waits** (found while planning). `settings.write` tells its listeners while holding the settings'
    lock, and the runner's listener nudged the driver by waiting for the service's event loop, which may itself be
    waiting for that lock (`_record`): a flow written from another thread (auto-accept, the owner's edit through the
    API) could hang the service. `Runner.nudge` from another thread now hands the nudge to a thread of its own.
13. **A run that ends** withdraws its batches' questions still waiting (the run no longer waits); their proposals stay
    waiting in their batch, can be decided from the command line, and join the flow's file for its next run.
14. **INTEGRATE's first message** names every deliverable of the boxes before it, in the order they ran: each by its
    path, the box that wrote it last and its size, or that it is not in the folder; `sees` still hands files whole.
15. **An edit** changes any of a box's settings but its id and its mark; the model's proposal is kept beside it
    (`original`), so the batch says what the owner changed.
16. **Commands:** `clank flow proposals NAME [--run N] [--full]`; `clank flow accept NAME [ID ...] [--all] [--prompt
    TEXT | --prompt-file FILE] [--title T] [--model M] [--mode M]` (an edit names one proposal); `clank flow reject
    NAME [ID ...] [--all]`. A box not started that the owner wants out of the flow is taken out of its file by hand
    (§9: "The owner may remove any box that has not started"); the Flow view's keys for it are step 6's.
17. **A DECOMPOSE's task is named what the tasks before it delivered** (added while building, task 7): §3 and §9 say
    each is "handed the deliverables of those before it", and a proposed task sees only the files it names; its first
    message names, by path, box and size, those of the tasks before it that it is not handed whole, rather than handing
    them all whole (a long series of tasks would make each first prompt longer and slower to read, design 0013 §7).
    At the review, design 0013 §3 and §9 were revised after approval to say so (its revision log).

## Review Focus

1. **The flow's surgery** (`joined`): the fan, the order kept whatever order they are accepted in, the lines rewired
   around a replaced task; the rules checking the result.
2. **Locks:** proposals staged from the API's threads while the driver runs; no settings write under the runner's
   lock; the nudge that never waits.
3. **The run held at the proposing box** until each proposal is decided, and the restart in between.
4. **The agent never deciding**, at the gateway and in the service.

### Task 12: The review's fixes

The review of step 4 (2026-10-20) found one fault to fix before it is pushed, and four smaller ones.

- [x] **Deciding proposals never hangs the service while a client follows its events** (the console, VS Code and the
  phone all do). The owner's decision (the route, on a worker thread) and the phone's *accept all* (its answer, on the
  thread that answered) held the proposals' lock while they wrote the flow and told the questions and events; the
  event stream hands each event to the service's event loop and waits until the loop takes it, and the driver, on that
  loop, waited for the same lock to hold the run at the DECOMPOSE: the service hung, every time. The driver now calls
  `hold`, `answered` and `set_aside` on a thread, what only reads a batch (`submitted`, `pending`, `ended`) reads it
  without the lock, and an answer given on the event loop is taken on a thread of its own. The test then found a second
  way to hang the same way: the settings' files told their listeners while holding their own lock, which the driver
  takes on the loop to read a flow (`_record`); they now tell them once it is released (design 0002 §2.2). Tests
  (`test_proposals_followed.py`, `test_settings.py`): a client follows the events, waiting for the loop at most five
  seconds for each, while the owner accepts through the route and while the phone accepts all, and the tasks run next;
  a listener of each settings change, and of a file that cannot be read, waits for another thread that reads the
  settings.
- [x] **A task proposed after a DECOMPOSE is never joined at a VERIFY that checks one of its tasks.** `joined` took the
  box the tasks join at from the first task's line on, so with a VERIFY after that task (auto-accept, or the owner
  accepting it alone while the DECOMPOSE works) a later task was wired into the VERIFY, which the rules took for the
  fan's join: the VERIFY, checking one task, then ran after both. That box is now found past the VERIFYs that check
  one of the tasks, and the rules refuse the task in their own words (a DECOMPOSE's tasks each lead to the box after
  them, §3), rather than accept the wrong wiring. Test (`test_proposals_join.py`).
- [x] **A proposal's mode is said where the owner decides it.** A model may propose a box with a mode of its own, and
  one in Auto has its session's changes accepted without review even while the workspace is in Review (§4); the
  question about a batch named each proposal's type, id, title, deliverable and model, but not its mode, so *accept
  all* could let one in unseen, and with auto-accept on only the event was left. Each proposal's line in the question,
  and its `flows.proposed` event, now say its mode when it has one ("in Auto: its changes are accepted without
  review"). Tests (`test_proposals_decided.py`, `test_proposals.py`).
- [x] **An edit keeps a deliverable** (call 4: an edited proposal is checked as a proposal is). `edited` let the owner
  empty a TASK's deliverable, or change a proposal's type to one that writes, with none; the rules took it, and such a
  TASK would be counted done whatever its session did. It is now refused as `read` refuses it ("a TASK writes a
  deliverable: name the files it writes in the folder"). Test (`test_proposals_decided.py`).
- [x] **Design 0013 §3 and §9 say how a DECOMPOSE's task is handed the deliverables before it** (call 17 departed from
  their words, recorded only as a call): revised after approval, as Claude's call, with the reason, in the sections'
  table, the revision log and the design index. The task is still handed what those before it delivered (decision
  0057), named by path, task and size as §5 names a file too large to give whole, rather than given whole.
