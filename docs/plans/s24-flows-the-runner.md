# Flows, step 2: the runner, one box after another, with gates: implementation plan

> At the owner's request (2026-10-19): the new menu, the Monitor and flows (the model orchestrator) built as quickly as
> possible, with the same care as always. This is design 0013's second build step. As for the earlier plans, the files,
> interfaces and tests by name and intent; the code is in the commits.

**Goal:** [design 0013](../design/0013-flows.md) §14 step 2: the flows component runs a flow in the service, one box
after another: each box a new session on the flow's own OpenCode server, its first message sent with the box's agent
and model and kept as a file; YOU boxes and gates as questions; a run's state and every try's first message and
deliverables in the run's folder; pause, stop and run from here; stale marks; `clank flow run|pause|stop`.

**Architecture:** A run is a readable JSON file, `CLANK_HOME/state/flows/<workspace>/<flow>/run-<n>/run.json`
(`runs.py`), beside each try's folder (`<box>/try-<k>/`: `first-message.md`, and `deliverables/` with the copies). The
runner (`runner.py`) is the flows component's background task: a driver that, whenever something changes (an operation
ended, a question answered, the owner's control, a flow's file changed), reads each active run and does its next thing:
start the box's operation, ask its question, go on, or end the run. Each model box's work is an operation,
`flows.box`, with the steps *model*, *server*, *session*, *work* and *collect* (decision 0061); YOU boxes, gates, a
failed box and a box whose *when done* waits are questions asked outside any operation, so they survive a restart. A
box's session is driven through the agents component (`Sessions`: a server started without a terminal, a session, its
first message with the agent and the model, a stop), and the runner hears the watcher's lines (`Sessions.listen`): a
box ends at its session's first `idle` after its first message. Its first message is built by `first.py` from the
type's instructions (`prompts/<type>.md`), the box's prompt, the files it sees, its deliverable and *accept when*, and
on a later try what happened to the last one. Deliverables are fingerprinted (`deliverables.py`): one counts only when
written during its try, and a finished box whose deliverable or settings changed marks the boxes after it stale; a
plan's progress (its ticks, its Log's lines, its header's `status`) is told apart from its other lines (§8).

**Tech stack:** Python 3.12, AnyIO, FastAPI, click, pytest; a fake bridge (`tests/fakes/bridge.py`) standing in for the
container's bridge as the fake platform's `inside`, with a scripted agent that writes files in a synthetic folder.

**Spec:** [design 0013](../design/0013-flows.md) §2, §4-§8, §10 and §14 step 2 (approved 2026-10-18); decisions
[0060](../decisions/0060-each-box-runs-in-a-new-session-on-the-flows-server.md),
[0061](../decisions/0061-the-runner-is-an-operation-per-box-in-the-service.md),
[0062](../decisions/0062-a-preset-per-box-switched-in-before-it-starts.md),
[0065](../decisions/0065-a-finished-box-goes-on-unless-a-gate-follows.md) and
[0066](../decisions/0066-a-flow-is-a-settings-file-in-clanks-home.md); design 0012's step 4, the bridge ([plan
s14](s14-monitor-the-bridge.md)): `prompt` sends the agent and the model, the watch says each session's status.

## Global Constraints

- Nothing here runs OpenCode, a container, Docker or a model: a GPU benchmark ran through them. The
  runner is tested against the fake bridge, the fake platform and synthetic folders only; nothing opens a window.
- No new dependency. Tests first, each test file's docstring naming the design sections it verifies, test names
  sentences.
- The owner is the sole author of every commit (no trailer). Each task is one commit; the generated files are
  regenerated by `uv run python -m tools.check --fix`.

## Claude's calls (2026-10-19)

1. **A driver, nudged.** The runner decides from each run's file what comes next whenever something changes, rather
   than holding a coroutine per run: a restart reads the same files and goes on the same way (decision 0061).
2. **A run is active from its start to its end**, waiting at a gate or paused included. A second flow's run is queued
   behind it ("one flow runs at a time", §6), says behind which, and starts when it ends.
3. **The order boxes run in** is the boxes along their lines (then and pass), a DECOMPOSE's tasks in the order of
   `boxes` (§3); a box is *after* another when it comes later in that order. A VERIFY's fail line is step 3's.
4. **Step 2's *model* step switches nothing:** it notes the preset the box names and what the main slot runs, in the
   operation's log; the switch is step 5's. The *server* step reuses the run's OpenCode server while it still runs
   without a terminal, else writes Clank's configuration and starts one (`Sessions.serve`), so a run starts one server.
5. **The agent and the model.** A box in Plan mode is sent to the `planner`, any other to `build`; the model is
   OpenCode's `clank/agent`, the gateway's role.
6. **A box ends at its session's first `idle` heard once the session was seen at work** (busy, or a message, a part or
   an error of its answer): the watch may say a quick run's busy and idle as one line (plan s14, call 4), so no `busy`
   is waited for, while an `idle` said before the answer began is not taken for its end (the self-review's fix).
7. **Written during its try:** a deliverable counts when its file exists and its fingerprint (content, size,
   modification time) differs from the one it had when the try started.
8. **A YOU box is done when its files exist and are not empty**, whenever the owner wrote them (the brief may be
   written before the run starts); its question offers *done* and *stop the flow*, and asks again, saying which file
   is missing, when one is.
9. **A gate's answers:** *approve and go on* (y), *send back* (b; the answer's words are the note, and the phone, which
   answers with an option only, sends back without one), *stop the flow* (s). *Edit, then approve* is approving after
   editing (step 7 opens the file in VS Code): the fingerprints taken when the gate is approved are the owner's (§8).
   *Send back* runs again the latest box before the gate that writes a file it shows (else the box before it), with
   the note, and every box after it.
10. **A failed box's gate:** *try again* (r; its words a note for the next try; past the box's tries, it says so),
    *take it as it is* (t), *skip the box* (k) and *stop the flow* (s). A skipped box is marked `skipped`.
11. **VERIFY and DECOMPOSE run in step 2 and fail** at their end, saying the verdict or the proposals come with steps
    3 and 4; their gate lets the owner take the deliverable as it is, or skip the box.
12. **A box whose *when done* waits** (or every box, with the flow's *wait after every box*) asks *go on* (y) or
    *stop the flow* (s).
13. **The owner's controls are events too:** `flows.run_steered` (pause, resume, from a box). Stop stops the running
    box's session (its try ends *stopped*, a failed try) and ends the run (`flows.run_ended`, stopped); *run from here*
    takes the flow's latest run back to the chosen box, whose next try and every box after it run again; a run paused
    goes on with `clank flow run`.
14. **A box's mode for its session:** the review answers a session's changes (and its subagents') by the mode the
    runner gave it, else by the workspace's (§4).
15. **Limits:** the time is checked against Clank's clock while the box works (every quarter second); the tokens are
    the sum of the output and reasoning tokens of the session's finished steps (its `step-finish` parts).
16. **Two flow settings:** `defaults.whole_up_to` (a text file the first message hands whole up to 40,000 bytes) and
    `defaults.copied_up_to` (a deliverable copied into the run's folder up to 5,000,000 bytes, larger ones kept by
    fingerprint), the sizes §5 and §8 call settings.
17. **After a restart**, the runner's start reads the run of each interrupted `flows.box` operation: a session still
    working, or one that ended, is followed and collected by a new `flows.box` operation that runs only its *work* and
    *collect* steps; a session gone fails its box at a gate. No session is started again.
18. **A run stopped while its box is still starting** (in its *model* or *server* step) starts no session: the box's
    try ends *stopped* before its *session* step (the self-review's fix).
19. **Changed files are read only when their size or time changed**, so looking for stale boxes, which the runner does
    whenever it drives, never reads a large deliverable again for nothing.
20. **A TASK's progress while it still works** (the review's fix): a plan the TASK found as delivered whose progress
    alone changed is not changed yet, whenever the runner looks; the TASK's end takes that progress as its own, and any
    other change counts at once.
21. **Run from here and send back take the boxes before the box run again as they stand** (the review's fix): their
    deliverables' fingerprints now, their settings, no mark of a change. The boxes that run again start from them, so a
    later change to them marks those boxes stale again.
22. **A box run again after a try that was done is told why** (`BoxRun.again`): "your owner sent it back at <gate>", or
    "your owner ran the flow again from this box" (or "from <box>, a box before this one").
23. **A run stopped while its box was ending, when the service stopped:** after the restart its box's session is
    stopped again, its try ends *stopped* and its operation is let go, so it runs again from a box.
24. **Tokens are kept in the run's file as they grow**, and a box followed after a restart counts on from them.
25. **A watcher started again** (its `synced`) has the runner read each followed box's session once through the bridge,
    off the watcher's thread: one that ended while no watcher ran has ended. Only a box whose first message was sent
    is read, so a new session idle before its run began is not taken for ended.
26. **A flow's servers:** a new run starts from its flow's last run's server, reused while it still runs without a
    terminal, so a flow keeps one server. Nothing stops it yet: restarting a server for a box's limits is step 5's.
27. **A gate says the try** its *send back* would run, "plan runs try 2 of 3", and says when it is its last or past its
    tries (§10).

## Review Focus

1. **The driver's nudges** come from other threads (the watcher's, the API's); a nudge lost would leave a run standing.
2. **Fingerprints and progress** (§8): a TASK's own ticks absorbed, a tick between boxes not.
3. **Restart**: an interrupted box followed, never started again; a gate still waiting after it.
