# Flows, step 8: each box prepared: implementation plan

> At the owner's request (2026-10-20): "The big thing that we need to implement is to make it so that each of the
> individual tasks are brand new sessions that get fresh context windows, but making sure that we are preparing each
> of these tasks with the correct context for the agent at that task to get the work done properly." The owner chose
> four additions to a box's first message, all built now. As for the earlier plans, the files, interfaces and tests by
> name and intent; the code is in the commits.

**Goal:** [design 0013](../design/0013-flows.md) §14 step 8 (added 2026-10-20): every box a model runs is handed the
flow's brief, once; a short map of where it sits in the flow; the handoff notes of the boxes before it (a VERIFY none),
which PLAN, TASK and INTEGRATE write at their end; and `clank flow prepare` shows each box's first message as it would
be sent now with its size against its model's window, `clank flow check` warning past a quarter of it and on a file
nothing gives a box.

**Architecture:** `first.py` stays a pure function of the flow, the box, the folder and what the run says: it gains the
map, the brief's section, the notes' section and the note's instruction, given the run (its boxes' states and
verdicts) and the notes already read. `handoff.py` (new) says where a box's note lives
(`.clank/handoff/<flow>/<box>.md`), which boxes write one, keeps the folder's `.clank/handoff/.gitignore`, and reads
the notes of the boxes before a box from their tries' copies (`handoff.md`), a VERIFY's verdict and a DECOMPOSE's
summary. `preparing.py` (new) builds the first message the runner sends (`message`: the notes read, then `first.py`),
so the runner and the preview send and show the same text; it previews every box (`preview`), counting each message
with the runtime, and finds the check's warnings. The runner sends `preparing.message`'s text, fingerprints the note's
file when the session starts, and at *collect* copies a note written during the try beside it (`Try.handoff`); a missing
note is said in the box's end event, never a failure. The runtime counts a text for a preset
(`Runtime.count_tokens`): by the engine's own route when the main slot runs that preset and its adapter names one
(llama.cpp's `/tokenize`, `EngineAdapter.TOKENIZE`), else an estimate from the model's calibration or Clank's plain
default, labeled. The service serves the preview (`GET /flows/{workspace}/{name}/prepare`) and the check's warnings;
`clank flow prepare` and `clank flow check` print them.

**Tech stack:** Python 3.12, AnyIO, FastAPI, click, pytest; the fake bridge and the runner's rig of plan s24; a tiny
HTTP server in the test for the engine's count.

**Spec:** [design 0013](../design/0013-flows.md) §2, §5, §6, §8 and §14 step 8 (revised 2026-10-20 at the owner's
request); decisions [0085](../decisions/0085-a-boxs-first-message-hands-the-brief-and-a-map-of-the-flow.md),
[0086](../decisions/0086-a-box-hands-on-a-short-note.md) and
[0087](../decisions/0087-a-first-messages-size-is-counted-by-the-engine-else-estimated.md); decision
[0063](../decisions/0063-verify-uses-the-preset-of-the-box-it-checks.md) (a VERIFY's independence); design 0012 §4
and decision [0067](../decisions/0067-the-monitor-reads-the-loaded-models-facts.md) (the context facts, the
calibration).

## Global Constraints

- Nothing runs OpenCode, a container, Docker, an engine or a model of the owner's: the runner is tested against the
  fake bridge and synthetic folders, the engine's count against a tiny HTTP server in the test; nothing opens a window.
- No new dependency. Tests first, each test file's docstring naming the design sections it verifies, test names
  sentences.
- Another build changes the runner at the same time (design 0013 steps 5 and 6): the runner's changes here stay small
  and in two places (the *session* step, *collect*), rebased often.
- The owner is the sole author of every commit (no trailer). The generated files are regenerated by `uv run python -m
  tools.check --fix`.

## Claude's calls (2026-10-20)

1. **The brief** is the file the flow's first box writes: a flow starts with a YOU (§3), and its `writes` is the brief
   (usually `BRIEF.md`). A later YOU box is the owner's work, not the brief. It is handed as any file is (whole up to
   `whole_up_to`, else by path and size), under its own heading, and `sees` no longer hands it.
2. **The order** of the first message: the type's instructions; where it sits in the flow; the brief; its task; the
   notes of the boxes before it; the files it sees; what the boxes before it delivered; its deliverable, *accept when*
   and its note; its last try (decision 0085).
3. **The map's lines.** The flow's title, the run when there is one, the box's place ("box 4 of 6"); each box before
   it, in the order they run: its number, id, type and title, and what it delivered as the run says (its files; a
   VERIFY's verdict; the tasks a DECOMPOSE broke the work into; the owner's approval at a gate; the owner's files of a
   YOU), or skipped, or taken as it was after a failed try; with no run (a preview), what it delivers. Then the box,
   marked, with its try; then each box after it with its title and how it uses this box's deliverable: it sees or shows
   one of its files, checks it (a fail sends this box back), is told of it (a later task of the same DECOMPOSE), or puts
   every deliverable together (an INTEGRATE). No prompt, file or session of another box.
4. **The note's file** is `.clank/handoff/<flow>/<box>.md`, `<flow>` the flow's name in its workspace. The runner
   writes `.clank/handoff/.gitignore` (`*`) when a box that writes a note starts and it is missing, as the annotations
   keep `.clank/annotations/` out of git.
5. **Who writes a note:** PLAN, TASK and INTEGRATE. A VERIFY's verdict and a DECOMPOSE's summary stand for theirs.
6. **A note counts when written during its try** (its fingerprint at the session's start, `Try.handoff_before`,
   against its fingerprint at *collect*, as a deliverable's); it is copied beside the try as `handoff.md` and kept on
   the try (`Try.handoff`), whatever the try's outcome. A missing note leaves the box's outcome as it is: its end's
   event adds "it left no handoff note".
7. **Notes handed on:** every later box but a VERIFY, in the order the boxes ran, each box's from its latest try in
   the run: its copy, else "it left no handoff note"; a VERIFY's latest verdict (its result and findings); a DECOMPOSE's
   latest summary; a box skipped is left out; a box not run yet in the run says its note comes once it has run. Each
   is quoted (`> `) under a heading naming the box, its type, its try and where it came from, cut at
   `defaults.note_up_to` characters (2,000), the cut said with the whole note's path.
8. **The preview's run:** the flow's active run (queued or running) when it has one, else none (as a new run would
   start); each box shown as its next try would be sent (`len(tries) + 1`, told what its last try was, as the runner
   tells it).
9. **The box's preset** for the window: its own, a VERIFY's the box it checks' unless it names one, else the flow's,
   as step 5 decides it (plan s27's `models.named` once it is on main); a box naming none takes the preset the main slot
   runs now, else the window is not known.
10. **Counting** (decision 0087): exact when the main slot is ready with that preset and its engine's adapter names a
    route to count (`TOKENIZE`, llama.cpp's `/tokenize`, its answer's `tokens` counted); else the model's calibration
    for a user's message (`tokens_per_character["user"]`, else the mean of its kinds); else 0.3 tokens per character.
    The engine asked for at most 10 seconds; a refusal or no answer falls back to the estimate, saying why.
11. **The check's warnings** never fail it: past a quarter of the window (`share > 0.25`); a file a box sees or shows
    that is not in the folder and that neither it nor a box before it writes. Problems first; warnings only once the
    flow keeps every rule.

## Review Focus

1. The first message the runner sends and the one the preview shows are built by one function.
2. VERIFY's independence: no notes, the map only.
3. Nothing loaded or switched to count; an estimate never shown as exact.
4. The runner's two changes, against the other build's.
