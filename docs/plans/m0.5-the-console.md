# M0.5: the console's shell: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans (executed natively in the session that
> wrote it). As for M0.2-M0.4, this plan gives the files, interfaces and tests by name and intent; the code is in the
> commits, written test-first.

**Goal:** `clank console` opens Clank's terminal console: a header with what runs, a menu of every screen, and the
screens M0 has (home, questions, history, Docker, machine, operations, the generic record screens, help), each live
from the one event stream, with `?` explaining any value. The menu also lists every screen the later milestones bring,
in red, each opening a page that says which milestone builds it and what it will do (the owner's request, 2026-10-11).
`clank console --snapshot` prints one frame as text.

**Architecture:** the console (`clank/console/`) is a client of the API and holds nothing of its own (design 0001
§5.1). `data.py` loads what it shows once (`ConsoleData`) and a `Follower` thread follows the event stream, turning
each event into fresh data (re-reading a topic from the API off the screen's thread) on a queue; the app drains the
queue at most four times a second, so redraws are capped (design 0001 §5.7), and animations are off. Every call to the
API runs in a worker thread, never on the screen's. `app.py` is the shell: header, menu, the page area (one page per
menu entry), the keys bar, the command palette and the explain panel. `menu.py` lists every entry: the screens M0 has,
and the planned ones with their milestone, what they will do and where they are designed. Pages are widgets in
`clank/console/pages/`; a component's own pages live in its `console/` folder and are declared in its `component.py`
(design 0002 §2.1, §2.15): Docker's in the workspaces component, the machine's in the machine component.
`snapshot.py` renders a frame as text (decision 0027). `clank.tcss` holds the styles; `CLANK_HOME/config/console.tcss`,
when it exists, is loaded after it, so the user's rules win (design 0001 §5.5).

**Tech Stack:** Textual 8.2.8 and Rich 15.0.0 (decision 0005, pinned in the lock); text snapshots (decision 0027, new);
the rest as before.

**Spec:** [design 0001](../design/0001-runtime-and-console.md) §5 (the console: §5.1 what it is, §5.4 explain anything,
§5.5 style files, §5.7 redraws and load, §5.8 without a screen), §8.1 (console tests); [design
0002](../design/0002-the-foundation.md) §2.1 (a component's console folder), §2.7 (presence), §2.15 (the console),
§3.2 (M0.5 and the console at the end of M0), §3.3 (what each later milestone brings).

## Global Constraints

- Everything of M0.1-M0.4's global constraints holds.
- The console never calls the API on the screen's thread; a slow or stopped service never freezes it.
- No animation, no spinner, no pulsing; at most four redraws a second (design 0001 §5.7, principle 6).
- Every action is also a command or a route; the console does nothing that cannot be done without it (§5.8).
- Planned entries are red through the style sheet (`.planned { color: red; }`), so the user can change it like any
  style.
- Console tests run against a real service on a free port, in a thread of the test (real HTTP and the real event
  stream), with the kernel built in the test (fake clock, fake container platform, a fixed machine profile); times are
  shown in UTC in tests, so snapshots do not depend on the machine's time zone.

## Review Focus

1. **The service stops while the console is open, or is not running when it opens:** the console says so in its
   header and reconnects when the service is back; `clank console` starts the service in the background when it is
   not running (unless `--no-start`). Pinned in Tasks 1 and 2.
2. **Events arrive in a burst (a busy operation's log):** the screen redraws at most four times a second and nothing
   is lost. Pinned by `test_a_burst_of_events_is_drawn_in_a_few_redraws_and_nothing_is_lost`.
3. **A question is answered in another client while the console shows it:** it leaves the console's list, and the
   history says who answered. Pinned in Task 3.
4. **A key pressed for an action whose call fails (the service refuses, or it is gone):** a message says why; the
   console stays usable. Pinned in Task 3.
5. **A narrow terminal (80 columns):** the menu and pages still fit without overlapping. Pinned by a snapshot at 80
   columns in Task 2.

### Task 1: The console's data, followed live

**Files:** decision record `0027-console-snapshots-are-text.md` and its index row (0022 marked); `pyproject.toml`
(textual); `clank/console/__init__.py`, `clank/console/data.py`; `clank/client.py` (closing a stream from another
thread); `tests/support/live.py`; tests `tests/console/conftest.py`, `tests/console/test_data.py`.

**Interfaces:** `ConsoleData` (`service`, `docker`, `machine`, `questions`, `history` (oldest first, at most 500),
`operations`, `kinds`, `connected`, `last_event`); `load(client) -> ConsoleData`; `Update(topic, data)`;
`Follower(client, after, updates)` with `run()` (blocking, for a thread) and `stop()`: each kept event becomes an
`event` update, and the topics it touches are read again from the API and sent as their own updates (`questions`,
`operations`, `docker`, `machine`, `service`); a live log line becomes a `log` update; a `reset`, or a connection lost
and found again, becomes `all` (everything read again); a lost connection becomes `connection` (False) and is tried
again every two seconds. `apply(data, update) -> set[str]`: the topics that changed. `live_service(kernel)` (tests):
the API served by Uvicorn on a free port in a thread, yielding a client.

**Tests:** loading reads every topic; a question asked in the service reaches the queue as an event and the fresh
list of questions; `docker.changed` brings the fresh Docker view; the end of a doctor run brings the machine; a live
log line arrives as `log`; when the service stops, the follower says the connection is lost, and when a service is
back on the same address it reloads everything; `apply` keeps at most 500 events.

### Task 2: The shell: header, menu, pages, keys, snapshots

**Files:** `clank/console/app.py`, `menu.py`, `snapshot.py`, `clank.tcss`, `pages/__init__.py`, `pages/planned.py`,
`pages/help.py`; `clank/kernel/components.py` (`console`: a function returning the component's pages);
`clank/cli/console.py` (`clank console`), `clank/cli/main.py`; tests `tests/console/test_shell.py`,
`tests/cli/test_console_command.py`, `tests/console/snapshots/`.

**Interfaces:** `MenuEntry(id, label, key, milestone, summary, designed_in)`; `MENU` (the screens M0 has, then the
planned ones: models, presets, providers and models, launch options, sampling, sessions, keys and layout (M1); tests
and trials (M2); requests and completion (M3); workspaces (M4); agents and modes (M5); changes (M6); network access
(M7); tool servers and skills (M8); phone and files (M9); setup guide (M10)). `ClankConsole(client, *, now=None,
zone=None, page="home", home=None)`: the header (`CLANK  service: up 2h14m · docker: running · questions: 1 waiting
… 11:42`, or `service: not running`), the menu (built entries with their key, then a `coming` section in red, each
with its milestone), the page area, the keys bar; keys `1`-`7`, `F1`, `?`, `Ctrl+P`, `q`; a click or Enter on an entry
opens its page. `PlannedPage(entry)`: red, the milestone, what it will do, where it is designed. `HelpPage`: every key
and what each screen shows. `render_text(app) -> str`. `clank console [--snapshot] [--page ID] [--width N] [--height
N] [--no-start]`.

**Tests:** the menu lists every screen M0 has with its key, and every planned screen in red with its milestone; a
planned entry opens a red page naming its milestone and what it will do; the header shows the service's uptime,
Docker's state and the questions waiting, and `service: not running` while the service is down; the style sheet in
CLANK_HOME is loaded after Clank's; animations are off; snapshots at 120 and at 80 columns; a burst of events is drawn
in a few redraws and nothing is lost; `clank console --snapshot` prints a frame; without a service, `clank console`
starts one in the background (and `--no-start` says how instead).

### Task 3: Home and questions

**Files:** `clank/console/pages/home.py`, `pages/questions.py`, `clank/console/actions.py` (calls made in worker
threads, failures shown as messages); tests `tests/console/test_home.py`, `tests/console/test_questions.py`.

**Interfaces:** `HomePage`: what runs (service, Docker with `s` to start or stop, machine with `d` for the doctor, and
`models` in red: milestone M1), what waits for you (the questions, the selected one answered with its options' keys,
`v` for its details), the latest history. `QuestionsPage`: every waiting question with its detail and options; the
same keys. Presence is sent on a key press at most once a minute (design 0002 §2.7).

**Tests:** home shows the three lines of what runs and the models line in red; an option's key answers the selected
question as you (console); a question answered elsewhere leaves the list and the history says who answered; `s` asks
Docker to stop and its question appears; a call the service refuses shows a message and the console stays usable;
presence is sent once for many keys; snapshots of both pages.

### Task 4: History, Docker, machine and operations

**Files:** `clank/console/pages/history.py`, `pages/operations.py`; `clank/components/workspaces/console/docker.py`,
`clank/components/machine/console/machine.py` (and their components' declarations); tests
`tests/console/test_pages.py`.

**Interfaces:** `HistoryPage`: every event kept, newest at the bottom, filtered by typing (`/`). `DockerPage`: the
state, versions and summary, each container with its owner, state and image; `s` starts or stops. `MachinePage`: the
profile and the last doctor's checks with what to do; `d` runs the doctor. `OperationsPage`: the newest operations
with their progress; Enter shows one's steps and log as it runs; `c` cancels, `r` retries.

**Tests:** each page shows its data and follows its events (a new event, a container started, a doctor run, an
operation's log line); the keys start their actions and say so; snapshots of each page.

### Task 5: Records, explain, and the command palette

**Files:** `clank/console/pages/records.py`, `clank/console/explain.py`; `clank/console/commands.py` (the palette's
provider); tests `tests/console/test_records.py`, `tests/console/test_explain.py`.

**Interfaces:** `RecordsPage`: the kinds (settings and state), the records of the chosen kind, and the chosen record's
values with each field's title. `Explanation(title, lines)`; `?` explains the focused value: for a record's field,
what it is (its description), its value, where it comes from (Clank's default or the user's file) and the file that
holds it; for the header and home lines, what they show and where from; for a question, why it is asked; for a planned
entry, its milestone and design section. The command palette lists every page and every action (start or stop
Docker, run the doctor, answer a question).

**Tests:** the records page lists the kinds and shows a settings record with its source and file; `?` on a field
explains it with its description and file; `?` on a planned entry names its milestone; the palette finds pages and
actions by name and runs them.

## Rulings made while building

- **Setup.** As in M0.4: work on `main`, a self-review at the end, interfaces and tests in the plan. Cost if wrong: a
  weaker review.
- **Task 1.** The event stream first says `connected` and announces who is connected as a live event
  (`service.clients`): the follower must know when it is live, and home shows the connected clients. Found while
  testing: the service waited forever for open responses on a stop, so a connected console would hold `clank stop` up;
  it now closes them two seconds after a stop. Cost if wrong: clients skip one message.
- **Task 2.** The menu lists the pages that exist (each page declares its entry) and then the planned ones, so each task
  added its pages to the menu. Re-reads after events are coalesced in one fetcher thread (the burst test showed 50
  events costing 50 reads). The follower ends the stream by shutting its socket down and closing its response (one
  wakes a blocked read on Linux, the other on Windows, as CI showed), and each thread closes its own connection
  (closing a client from another thread while it connected leaked a socket). Cost if wrong: none.
- **Task 3.** A key the page acts on goes to the page first when the focus is in it (digits there answer numbered
  options; from the menu they open pages); letters always go to the page. Actions report on a message line of the
  console's own instead of Textual's toasts, which are not part of a rendered frame; errors are bold yellow, keeping
  red for planned entries. Presence the user did not ask for is quiet. Cost if wrong: Tab before a digit answers.
- **Task 4.** Components declare their pages (`Component.console`, imported only by the console; a test proves the
  service never loads Textual). Shared helpers moved to one place each instead of being copied (the doctor's marks,
  an image's name). Cost if wrong: none.
- **Task 5.** Every settings record carries where the user's file is or would be, and every kind names its defining
  class, so `?` can say where a value is kept and defined. The records page shows values; changing settings from the
  console comes with the first page that needs a form. Cost if wrong: a later task.
- **After Task 6.** CI on Linux showed keys arriving before a focus change and frames taken between a text change and
  its layout; the tests now wait for focus (`focus_on`) and for a stable frame (`frame_when`). It also exposed a real
  fault: the records page read a record twice and the second rebuild dropped the highlighted value; it now reads what
  it shows only when an event says it changed, and keeps the highlight. Cost if wrong: none.

## Final review

A self-review of all of M0.5 against design 0001 §5 and design 0002 §2.15, §3.2 and the Review Focus above: each
Review Focus item has its test (the service down or absent, a burst of events, an answer from elsewhere, a refused
call, 80 columns), a run of `clank console --snapshot` against a throwaway home started its own service and read the
real Docker Desktop, and CI passed (run for 8e3b7f5). One finding fixed during the review: presence that fails was said
on the message line, repeating the header. Deferred (minor): a step cut short by a cancel is recorded as failed (the
operation itself says canceled; the step table allows running, done and failed only); the console's own settings (the
redraw limit, which panels show, the keys) come with the layout page in M1; the history page's filter box is always
shown.
