# Flows, step 3: VERIFY and its loop: implementation plan

> At the owner's request (2026-10-19): the new menu, the Monitor and flows (the model orchestrator) built as quickly as
> possible, with the same care as always. This is design 0013's third build step. As for the earlier plans, the files,
> interfaces and tests by name and intent; the code is in the commits.

**Goal:** [design 0013](../design/0013-flows.md) §14 step 3: a VERIFY box gives its verdict with `flow_verdict`
(Clank's MCP server, through the gateway's `/flows/` routes, to the service), *pass*, or *fail* with numbered findings,
and the lines of the brief and of *accept when* it checked (`criteria`, §9 as revised for §12's **The brief,
checked**); a fail takes the VERIFY's fail line back to the box it checks, whose next try is handed the findings; when
that box's tries are used up, the fail goes to a gate instead (§3, §10); a pass goes on; a VERIFY that ends without a
verdict fails. Also: *accept when* as a command the runner runs in the container after a box (§4); each try's copies
compared, the gate saying what changed since the last try (§8, §10).

**Architecture:** A verdict is part of the run's file: the VERIFY's try holds it (`verdicts.py`: `Verdict`,
`Criterion`), and the try's folder keeps it as `verdict.md` (§8). The service gives a verdict to the VERIFY box at work
in the workspace that sends it (one box at a time, §6, §9): `Runner.verdict`, behind `POST /api/v1/flows/verdict`; the
gateway forwards `POST /flows/verdict` there as the client `agent` and refuses anything else under `/flows/` (403,
decision 0020), as it does for Notion; the MCP server's `flow_verdict` asks the gateway, naming its workspace. The
driver takes the fail line from the run's file alone, as it does everything (plan s24, call 1): a VERIFY whose try gave
a fail is *failed*, and the driver sends the checked box back with the findings while it has tries, else asks the
loop's gate. *Accept when*'s command runs in the *collect* step (`accepting.py`); two tries' copies are compared by
`diffs.py`, behind `GET /api/v1/flows/{workspace}/{name}/diff` and `clank flow diff`.

**Tech stack:** Python 3.12, AnyIO, FastAPI, click, Python's `difflib`, pytest; the fake bridge (`tests/fakes/bridge.py`)
gains the commands the runner runs in the container.

**Spec:** [design 0013](../design/0013-flows.md) §2-§5, §8-§10 and §14 step 3 (approved 2026-10-18; §9 and §12
revised 2026-10-18: `flow_verdict` gains `criteria`); decisions

## Claude's calls (2026-10-19)

1. **Whose verdict.** A verdict goes to the VERIFY box at work in the workspace its MCP server names (one box runs at a
   time, §6; the server knows its workspace, not its session, §9), while its try runs: its first message sent, its end
   not yet collected. Otherwise it is refused with why (409), in words the model can act on: no box works there, the
   box at work is not a VERIFY, its try has ended. The newest verdict of a try counts; each is an event.
2. **A verdict's shape.** `result` is `pass` or `fail`; `findings` are words, numbered in their order; a fail needs at
   least one, each one thing to fix; a pass may carry findings, kept as remarks, and told to no box. `criteria` lists
   lines, each `{line, met, evidence}`: the line of the brief's limits or of *accept when*, as the VERIFY quotes it,
   whether it is met, and the figure, line or file that shows it. Matching them to the brief's lines is the Flow view's
   (step 6). A refusal says what to fix ("a fail lists its findings, each one thing to fix").
3. **The fail line, from the run's file.** A VERIFY's try that gave its verdict is *done* (its session did its work);
   with a fail, the VERIFY's box is *failed* ("it found plan's try 2 wrong: 3 findings"), and the driver takes its fail
   line: while the checked box has tries, it and every box after it up to the VERIFY run again, as *send back* runs
   them (the boxes before taken as they stand, plan s24 call 21); at the cap, the VERIFY's failed gate is the loop's
   gate (§10): *one more try* (past the cap: the loop goes round once more, with the owner's words as a note), *take it
   as it is* (the checked box's files stand, the flow goes on along the pass line), *skip the check*, *stop the flow*.
4. **Tries** are every try of the checked box in the run, as the gate's *send back* counts them (plan s24, call 27):
   with 3, the third fail goes to the gate, never to a fourth try.
5. **What a try is told.** The checked box's next first message says that try *k* was done and which VERIFY found it
   wrong, then the findings, numbered. The VERIFY's own next try is handed its last findings too, to check how each was
   answered (board D3's report), and is still never handed the checked box's session.
6. **At the loop's gate the checked box's files are the owner's** to edit, as a gate's shown files are (plan s24, task
   7): they mark nothing stale while it waits, and *take it as it is* takes them as they stand then.
7. **`flow_verdict` for the planner.** It is not marked read-only (it changes Clank's state, as Notion's proposals do),
   but the planner's rules allow it by name, since it writes nothing in the folder (§9: "its rules gain them"): a
   VERIFY runs in Plan mode by default (§4).
8. **The gateway forwards `POST /flows/verdict` only** for now, as the client `agent`, recorded as the agent's session;
   anything else under `/flows/` is 403. Step 4 adds reading and proposing.
9. **The accept command** runs in the workspace's container, in its folder (`sh -c`), in the *collect* step, after the
   deliverables were found written during the try, with the box's time limit; exit 0 passes. Its command, exit status
   and output are kept as `accept-command.txt` in the try's folder. When it fails, the box fails, and its next try is
   told the command, how it ended and the last 40 lines of its output (at most 4,000 characters).
10. **The diff** of two tries' copies of a file is Python's unified diff (three lines of context). Lines changed are
    counted per change: a replaced block counts its longer side, so "changed since try 1: 7 lines" reads as board D3.
    By default it compares the box's last two tries that kept a copy of the file; a try that kept the file by its
    fingerprint only, or wrote no such file, says so. A gate shows, beside each file it shows that changed since the
    last try, how many lines changed.

## Review Focus

1. **The loop's bookkeeping**: the checked box's tries counted once; the cap gate's answers; a restart between the
   VERIFY's end and the loop taken (the driver decides from the run's file).
2. **The gateway's refusal** of everything under `/flows/` but the verdict.
3. **A verdict given to the right box**, never to a box that has ended, nor to another workspace's run.

### Task 8: The review's fixes

The review of step 3 (2026-10-19) found two faults to fix before it is pushed, and three smaller ones.

- [x] **A gate's figures off the service's event loop, and cheap.** A gate's "changed since try 1" was counted on the
  event loop with `difflib` matching every line exactly, which takes minutes on a file of repeated lines (186 seconds
  for 102 KB of pretty-printed JSON), holding the whole service meanwhile. The driver now counts a gate's figures in a
  thread before it asks (`_ask_showing`), and `compare` drops the lines both copies begin and end with, then matches the
  rest exactly only while each side has at most 1,000 lines; past that it leaves out lines repeated through the file
  as anchors (`difflib`'s *autojunk*, as its unified diff does). Tests (`test_diffs.py`): 200 KB of such a file is
  counted within seconds; a gate's figures are counted outside the event loop.
- [x] **An accept command that can be stopped.** The command ran inside the *collect* step's thread, which nothing
  stopped: the owner's stop, a cancel from the Operations page and the service's own stop all waited for it, up to
  the box's time, and a stopped run's try was then recorded as done. The command now runs in a thread of its own,
  while the step looks a few times a second at the run's stop and the operation's cancel; on either, or when the
  service stops, it is ended in the container (`accepting.end`: `timeout`, which the command runs under, is sent
  `TERM`, and it ends every process the command started, killing them 10 seconds later if need be), the thread is let
  go, and the try is recorded as stopped. Tests (`test_accept_command.py`): a stop, a cancel and the service's stop
  during the command each end it in the container at once, and the first two record the try as stopped.
- [x] **A deliverable the accept command rewrote** (a formatter, a generator). The try's fingerprints were taken before
  the command and its copies after it, so they disagreed, and the box was marked changed as soon as it was done. Both
  are now taken after the command, and the command's record says which deliverables it changed (`Commanded.changed`,
  and `accept-command.txt`). Test: a command that rewrites `grid.json` leaves the box done, unchanged, its copy
  matching its fingerprint, and says it changed it.
- [x] **A criterion that is not what the route takes** was refused with "the request is not what this route takes",
  naming no field, since the client keeps only the message of a 422. The service now reads each criterion itself and
  refuses, naming the criterion and the field: one that is not an object, a key a criterion does not take (put it in
  its evidence), a `met` that is not true or false (the words true, false, yes, no, met and not met are read as
  such). Tests (`test_verify.py`, `test_flow_tools.py`).
- [x] **A verdict while the VERIFY's try has not begun** (its first message not yet sent) is refused, and nothing is
  kept; the test of a verdict after its try ended reached only the refusal for a run with no box at work. Test
  (`test_verify.py`).
