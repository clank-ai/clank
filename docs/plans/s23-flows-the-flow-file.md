# Flows, step 1: the flow file: implementation plan

> At the owner's request (2026-10-19): the new menu, the Monitor and flows (the model orchestrator) built as quickly as
> possible, with the same care as always. This is design 0013's first build step. As for the earlier plans, the files,
> interfaces and tests by name and intent; the code is in the commits.

**Goal:** [design 0013](../design/0013-flows.md) §14 step 1: a flow is a readable settings file in Clank's home,
`CLANK_HOME/config/flows/<workspace>/<name>.json`, of the kinds `Flow`, `Box` and `Line`, with its schema; Clank ships
a template; a flow that breaks §3's rules is refused, naming the file, line and field; `clank flow list|show|check`;
the glossary's new words.

**Architecture:** The kernel's settings files learn one thing: a kind whose records are grouped one folder deeper
(`GROUPED_BY = "workspace"`), each named `<workspace>/<name>`; so a flow is read, read again when its file changes,
written over its revision and recorded like every settings record (design 0002 §2.2, decision 0066). A new component,
`flows` (`clank/components/flows/`, in the shape of every component), declares the kind and, for now, only reads and
checks flows: the rules that need nothing but the file are the kind's own validation (so a hand-edited file that breaks
them is reported like any settings file that does not read, and the last good flow stays in force); the checks that
need other records (the presets, the workspace) are the component's, behind `/flows/` routes that `clank flow` calls.
The runner, its events and everything a box does are step 2 and after.

**Tech stack:** Python 3.12, Pydantic 2 (a model validator raising its problems with their places), FastAPI, click,
pytest.

**Spec:** [design 0013](../design/0013-flows.md) §1-§4, §11 and §14 step 1 (approved 2026-10-18); decisions
[0057](../decisions/0057-a-flow-is-a-chain-of-boxes.md), [0061](../decisions/0061-the-runner-is-an-operation-per-box-in-the-service.md)
to [0066](../decisions/0066-a-flow-is-a-settings-file-in-clanks-home.md); boards D1 and D2
([FlowRun.dc.html](../design/boards/FlowRun.dc.html), [FlowNode.dc.html](../design/boards/FlowNode.dc.html)).

## Global Constraints

- No new dependency. Tests first, each test file's docstring naming the design sections it verifies, test names
  sentences. Tests use temporary homes and synthetic folders only; nothing opens a window; no test needs Docker or a
  model.
- The owner is the sole author of every commit (no trailer). Each task is one commit; the generated files (schemas,
  `vscode/src/core/kinds.ts`, `docs/CODEMAP.md`, `docs/TESTS.md`, `docs/API.md`) are regenerated by
  `uv run python -m tools.check --fix`.
- A flow file is written in the settings files' one fixed format: "schema" first, the fields in the kind's order, only
  the values that differ from the defaults, two-space indents.

## Claude's calls (2026-10-19)

1. **A flow is a grouped settings record.** The kernel's `Settings` gains `GROUPED_BY` (empty for every other kind):
   a flow is `config/flows/<workspace>/<name>.json`, its id `<workspace>/<name>`; a file directly in `config/flows/`
   belongs to no workspace and is reported as a file that does not read. The record routes take such an id
   (`/records/flow/myproject/new-study`), and every id a client writes is checked to be plain names (no `..`, no
   `\`), since an id with a `/` now reaches a path.
2. **§3's rules are the kind's validation**, each problem raised at its own place (`lines.3.to`), so the settings
   files name its line. The checks that need other records are the flows component's: a preset that does not exist
   (named by its id or its title, as presets are everywhere), a `workspace` that is not the folder's, a workspace
   Clank does not know.
3. **`Box` and `Line` are parts of a flow's file**, defined once in Pydantic as kinds are, but not records of their
   own: they are not in the registry, and only `flow` has a schema file.
4. **DECOMPOSE's accepted tasks are written fanned out:** a line from the DECOMPOSE to each task and from each task to
   the box after them; they run in the order of `boxes` (§3's two exceptions are exactly a VERIFY's fail line and this
   fan). Before any task is accepted, the DECOMPOSE has one line on, as in §11's example.
5. **The file's fields** follow §4 and §11: a box's `writes` is its deliverable's files and `holds` what they hold, in
   words; `accept_when` is a list (one thing that must hold per line, as board D2 shows it) and `accept_command` the
   optional command; `when_done` is `go on` or `wait`; `mcp_servers` the workspace's MCP servers it gets (empty: the
   workspace agent's own); `proposed` marks a box accepted from a proposal (its run, the box that proposed it, and
   who accepted it: you or auto-accept, §9). The flow's `defaults` give the model, 3 tries and limits of 30 minutes
   and 200,000 tokens a box (§11's example). Network is no setting until M7 (§4); the link to the next flow
   (decision 0058) is added with the step that makes one.
6. **The flow's first box is a YOU** (§2: "Every flow starts with one"), and a box done by the owner (YOU, GATE) names
   no model and no mode.
7. **A file a box writes, sees or shows is named from the folder with `/`**: an absolute path, a drive, `..` or a `\`
   is refused as outside the folder (the folder is `/workspace` in the container and a Windows path on the host).
8. **The template** is `clank/defaults/templates/flow.json`, §11's shape for any workspace (no workspace named), kept
   outside `defaults/flows/`, where a file would belong to no workspace.
9. **A flow written through the generic record route** (`PUT /records/flow/...`) is checked by the kind's rules but
   not for its presets; the flows component's own save (the Flow view, step 6; proposals, step 4) checks both.
   *Superseded by the review (call 11):* §14's step 1 says an unknown preset is refused, so every save checks it.
10. **(Review, 2026-10-19.) A component may check a kind's records against other records in the kernel's settings
    files** (`SettingsFiles.check_with(kind, check)`, the check given a record's id and values and naming each place
    that is wrong), rather than a save path of the flows component's own: so a flow naming a preset that does not exist,
    a preset of another slot, or a workspace not its folder's is refused by every save, the generic record route
    included (409, each field named), and a file edited by hand into one is reported (`settings.invalid`, with its line
    and field) while the last good flow stays in force, as a file that breaks §3's rules is. Adding the check reads the
    files again, and a record read before it was added is never kept when the check finds it wrong. The check reads
    the preset and workspace records alone, as it runs at every read of the files.
11. **(Review.) A flow's file that is gone** (deleted by hand) is listed, shown and checked as gone, not an error, until
    the service reads the folder again (within seconds).
12. **(Review.) A VERIFY has both its lines** (§3: "A VERIFY has two lines: pass to the box after it, and fail back
    to the box it checked"): one without its fail line is refused, naming the box, since step 3's loop needs it; one
    without its pass line too, so a flow never ends with a VERIFY (it ends with a gate, board D1). The owner may
    loosen this if a flow should end with a check.
13. **(Review.) A DECOMPOSE fans out to TASK boxes only** (§2's table: DECOMPOSE makes "proposed TASK boxes"); a fan
    to any other type is refused as a box with two lines on.

## Review Focus

1. **An id with a `/`** reaching the record routes: `..`, a `\` or an empty part never leaves the kind's folder.
2. **A flow that breaks two rules at once** (a line naming no box, and that box's VERIFY): every problem is named once,
   none hides another, and none is a crash.
3. **A file edited by hand into a broken flow while the service runs:** the last good flow stays in force, and
   `clank flow list` and `check` say why the file does not read.

- [x] **Files:** `clank/kernel/records.py` (`Settings.GROUPED_BY`); `clank/kernel/settings.py` (`_files` reads
  `<folder>/<group>/*.json`, a file directly in the folder is a problem; ids checked on write and delete; `line_of`

  revision and refused over another; an id that climbs out of the folder, or names no group, is refused; the record
  routes read and write a grouped record by its id.
