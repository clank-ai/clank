# Flows, step 5: a model per box: implementation plan

> At the owner's request (2026-10-19): the new menu, the Monitor and flows (the model orchestrator) built as quickly as
> possible, with the same care as always. This is design 0013's fifth build step. As for the earlier plans, the files,
> interfaces and tests by name and intent; the code is in the commits.

**Goal:** [design 0013](../design/0013-flows.md) §14 step 5: each box runs on its own preset. The *model* step of
`flows.box` switches the main slot to the box's preset before the box starts, only while no request is in flight on the
slot and the owner's own session in the workspace is idle, saying what it waits for; a failed switch returns the slot
and leaves the box failed at a gate; after a switch, the owner's window is told, on This folder and in VS Code, naming
a preset too small for what the owner's session holds, its configuration refreshed only when it next starts. The
*server* step starts the flow's OpenCode server with the box's context and output limits, and again only when they
differ; each box gets its own MCP servers on that server.

**Architecture:** Which preset a box runs on is a pure function of the flow (`models.py`: `named`, `switches`): its
own, a VERIFY's the box it checks' unless it names another (decision 0063), else the flow's. The runner's *model* step
(`runner.py`, `_load`) compares it with what the main slot runs (the runtime's slot state); when they differ it waits,
a second at a time, while the gateway's activity shows a request in flight on the slot, an operation changes
the slot, or a session of the workspace that is no box's works (the agents' `Sessions.working`), saying so in the run's
file (`Run.waits_for`) and an event (`flows.model`, *waits*); then it starts the runtime's `runtime.switch` and waits
for its end, which says *switched* or *failed*. A switch done tells the owner's window (`Agents.model_changed`: the
event `agents.model_changed`, a notice the review's view carries until the window next starts). The *server* step
(`_serve`) knows the limits the flow's server was started with (`Run.server_limits`): the same, it is reused; others,
it waits for any session at work on it, ends it (`Sessions.end_server`, never a window) and starts one again with
Clank's configuration written for the slot as it runs now, the run log saying so (`flows.server`); then it connects the
box's MCP servers on that server alone and disconnects the others (`Agents.box_tools`), Clank's own always kept. Each
try names the preset it ran on and the MCP servers it had (`Try.preset`, `Try.tools`).

**Tech stack:** Python 3.12, AnyIO, FastAPI, click, pytest; TypeScript and Node's runner for the extension; the fake
bridge and the runner's rig of plan s24, and the fake engine of the runtime's tests (real `runtime.switch` operations
between two presets of a tiny model, no GPU).

**Spec:** [design 0013](../design/0013-flows.md) §4, §5, §7 and §14 step 5 (approved 2026-10-18); decisions
[0062](../decisions/0062-a-preset-per-box-switched-in-before-it-starts.md) and
[0063](../decisions/0063-verify-uses-the-preset-of-the-box-it-checks.md); design 0001 §4.2 (the switch, its *wait*);
what steps 2-4 built ([plan s24](s24-flows-the-runner.md), [plan s25](s25-flows-verify-and-its-loop.md), [plan
s26](s26-flows-proposals.md)).

## Claude's calls (2026-10-20)

1. **A box's preset** is its own `model`, a VERIFY's the box it checks' (that box's own, else the flow's) unless it
   names one (decision 0063), else the flow's `defaults.model`. A box that names none runs on what the main slot runs
   when it starts, as in step 2: nothing is loaded for it, and its try says what that was.
2. **The main slot** is the one the gateway routes the role `agent` to (`main` by default), and the switch is the
   runtime's own `runtime.switch` on it, started by the runner (`clank (flow runner)`), so it is the same operation
   the owner starts from F8, with its plan, its steps and its return to the last configuration that worked.
3. **What the switch waits for**, checked every second (§7, decision 0062): a request the gateway has in flight
   on the slot (one waiting for it, held for a paused session, reading or answering: a held request belongs to a
   session the owner paused, which is waited for too); an operation that already changes the slot (a load or switch
   started elsewhere: once it ends, the slot may run the box's preset); and a session of the workspace at work (busy
   or retrying, as its watcher last said) that is no session of a flow's box nor a subagent of one: the owner's own,
   from the window, the phone or VS Code. While it waits, the run's file says so (`waits_for`: "waiting for your
   session … to be idle to load …") and one `flows.model` event says it each time what it waits for changes.
   Revised at the review: a gateway that runs but did not say what it has in flight (its activity timed out) is waited
   for too ("waiting for the gateway to say what is in flight on the main slot …"), since no answer is not none in
   flight; a switch refused as an operation took the slot a moment ago (`Busy`) is waited for and started again.
4. **The owner's stop while the box waits** ends the box's try *stopped* at once. **While the slot switches** (revised
   at the review), the switch the runner started goes on to its end in the runtime (stopping an engine halfway is not
   safer than finishing), and the stop, or a cancel, waits for that end: the run log says the switch ended (*switched*
   or *failed*), the owner's window is told of a switch done (call 6), the try names the preset loaded for it, and
   then the try ends *stopped*.
5. **A failed switch** ends the box's try *failed* with the switch's own words (the engine's reason, and that the slot
   went back to the last configuration that worked), so it waits at a gate; the `flows.box` operation fails in its
   *model* step.
6. **The owner's window is told** after every switch the runner made, whether or not a window runs: the event
   `agents.model_changed` (subject the workspace; VS Code shows its summary as a notification), and a notice the
   review's view (`GET /agents/review`) carries, which This folder shows under "Then work" until OpenCode is next
   started there (`prepare`, which writes its configuration) or another switch replaces it. It names each root session
   of the workspace that is no box's whose context holds more tokens than the new preset's context (its last finished
   step, the Context window's *used*) as too small for it. The notice is kept by the service, not in a file: after a
   restart, the event history still says it.
7. **The window's configuration** (OpenCode's file in the container's home, read when an OpenCode starts) is written
   when the flow's server is started, as in step 2, so it always says the slot as it runs; a running window keeps the
   configuration it started with (Clank runs OpenCode without its file watcher, and asks nothing of the window), so it
   changes only when it next starts (to measure, below).
   The flow's server takes that same file: two servers each with a configuration of its own wait for the measurement
   below, and decision 0092 says why one file serves both until then.
8. **The server's limits** are the context and output the configuration gives the model: the slot's preset's, after
   the *model* step, else Clank's fallback when no model runs. The run keeps them with the server (`server_limits`);
   a server whose limits were not kept (one started before this step) is started again. Revised at the review: they
   hold whether the model reads images too, which the configuration says (`attachment`), so a model that reads them
   where the server's did not (or the reverse) gets the server started again; its title alone does not (it is only
   shown: every request reaches the slot by its role). They are read again once the wait of call 9 is over, so the
   run keeps those the server is started with.
9. **Starting the server again** waits, as a switch does, for any session at work on it that is not this run's (the
   phone may have started one there), then ends it: `pkill` of its `opencode serve --port N` in the container, asked to
   end and ended after ten seconds, never a window (`opencode --port`), refused when the port runs a window. No image
   change is needed: the container's `pkill` already ends windows for the one-window rule.
10. **A box's tools.** `mcp_servers` empty: every MCP server the workspace's agent gets; else those it names, and
    Clank's own server (`clank`) always, since it carries the flow's tools (§9: any box may propose, a VERIFY gives its
    verdict with it). A name the workspace's agent does not get fails the box at its *server* step, saying why (the MCP
    servers page gives it). Only the flow's server is changed (the bridge's `mcp-start` and `mcp-stop` on its port), and
    only what differs from its state now; a server that fails to connect is said in the operation's log and left out of
    the try's `tools`. Revised at the review: that holds when the bridge itself reports the failure (an HTTP error of
    OpenCode's, or a connect past its 90 seconds), said in the bridge's words; one it fails to disconnect stays
    connected, said so; and an empty list is read as no list, every server the workspace's agent gets.
11. **Events:** `flows.model` (*waits*, *switching*, *switched* with its seconds, *failed* with why) and `flows.server`
    (the server started, or started again with the old port and why), each with its run and box; `agents.model_changed`
    is the agents', with the workspace as its subject.
12. **The switches a flow makes, before it runs** (decision 0063: "the switches' cost shown before the flow is saved"):
    `clank flow show` lists them along the boxes' order, from what the main slot runs now, each with the last time its
    preset took to load, and `clank flow check` says how many; the Flow view draws them in step 6. Revised at the
    review, as §7 records a switch: that time is the preset's last whole switch (or load) into the main slot, from the
    operation's start to its end, and only when none is among the newest operations its engine's last start to ready,
    said so (`whole`).

13. **A wait the service's stop cut short** (found at the self-review): a box's operation let go (it ended, or a restart
    found it interrupted) takes the run's `waits_for` back, so a run never says it waits for something after a kill.

## Review Focus

1. **The waits** (`_load`): every condition looked at again after each wait, a switch started only once, the run's stop
   and the operation's cancel heard while waiting.
2. **The owner's sessions** (`Sessions.working`): a box's session, and its subagents, never taken for the owner's.
3. **Ending a server** (`end_server`): never a window, and only once no session at work on it is not the run's.
