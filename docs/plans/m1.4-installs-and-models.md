# M1.4: installs and models: implementation plan

> As for M1.1-M1.3, this plan gives the files, interfaces and tests by name and intent; the code is in the commits,
> written test-first.

**Goal:** engines and models get onto a host the way design 0003 §7 says: KVMem's existing build is adopted (checked,
recorded, left where it is); NInfer is built by its recipe; model files are downloaded (asked first, resumed,
verified) or adopted where the user already has them (their checksum verified once). On this machine at the end: KVMem
v0.16.0-rc1 adopted in `Ubuntu-22.04` with its GGUF files, NInfer v1.4 built in `Ubuntu` (24.04) with its `.ninfer`
file, and NInfer's recording made from the build.

**Architecture:** design 0003 §7, with one change found while building (decision 0032): a recipe builds its engine in
an environment of its own under the host's Clank folder, made by micromamba from conda-forge (the compiler, CMake, the
CUDA toolkit at the release's exact version, the libraries), so an install needs no root, changes nothing outside
Clank's folder, and runs on any distribution. A recipe is a readable file (`clank/recipes/<setup>/<version>.json`): the
environment's packages, the pinned source, the commands, the program it makes, how it is verified. An install is the
operation `runtime.install` (show what it will do, ask first, then each step with its output in the operation's log, on
half the cores at low priority); a download is `runtime.download`.

**Tech Stack:** what M1.3 uses; on the host, micromamba 2.9.0 (a single static program) and conda-forge's packages,
fetched by the recipe into the host's Clank folder.

**Spec:** [design 0003](../design/0003-the-runtime.md) §5 and §7; design 0001 §7.4-§7.5; decisions 0010, 0030, 0031.

## Global Constraints

- Everything of M1.3's global constraints holds.
- An install and a download say what they will fetch (and its size) and ask first; nothing is installed with root, and
  nothing is written outside the host's Clank folder (an adopted install stays where it is, untouched).
- A model file is used only once its checksum is the catalog's; a download resumes after an interruption.

## Review Focus

1. **A download cut off halfway:** the next one resumes from what it has, and the file is used only once verified.
   Pinned in Task 3.
2. **A downloaded file whose checksum differs:** refused, kept aside, said. Pinned in Task 3.
3. **An adopted engine that is not the version its adapter knows** (another commit, or its `--help` lacking a flag):
   refused, saying what differs. Pinned in Task 2.
4. **A build step that fails:** the install stops there, its last lines said, and running it again goes on from the
   step that failed. Pinned in Task 1.
5. **The user answers no:** nothing is fetched or built. Pinned in Task 1.

### Task 1: Recipes, and the install operation

**Files:** decision record `0032-engines-build-in-environments-of-their-own.md`; `clank/recipes/ninfer-rtx5080/v1.4.json`,
`clank/components/runtime/recipes.py`, `installing.py`, the hosts' `run_step`, the kernel's `stream_command`; tests
`test_recipes.py`, `test_install.py`, `test_engine_commands.py`, the host contract.

**Interfaces:** `Recipe` (setup, version, summary, download, steps (name, run, makes, env), program, library path,
deviations); `recipes()`; `runtime.install` (plan and ask, run each step, verify, record) under the lock
`install:<setup>@<version>@<host>`; `GET|POST /runtime/installs`; `clank engine install SETUP --version V --host H
[--yes]`, `clank engine list`.

**Tests (a recipe of small shell steps on the local host):** the install shows its steps and asks; "no" leaves nothing
done; "yes" runs each step with its output in the log and records the install with its program; a failing step stops
the install with its last lines, and a second install goes on from that step.

### Task 2: Adopting an engine already there

**Files:** `installing.py`; tests `test_adopt.py`.

**Interfaces:** `runtime.adopt` (check the program is there, its help against the adapter, and its checkout's commit
against the adapter's version; record it as adopted, with any local changes); `POST /runtime/installs/adopt`; `clank
engine adopt SETUP --version V --host H --program PATH --folder F [--source S] [--library-path L]`.

**Tests:** an adopted program whose `--help` lists the adapter's flags, built at the adapter's commit, is recorded
where it is; local changes are recorded with it; another commit, a folder that is no checkout, a missing flag and a
missing program are each refused saying what differs.

### Task 3: Model files: downloads, and adopting files already there

**Files:** `clank/components/runtime/modelfiles.py`; tests `test_download.py`.

**Interfaces:** `runtime.download` (show the size and the free disk, ask, fetch with resuming into `<file>.part`,
verify the SHA-256, keep it as the file); `runtime.verify` (a file the user already has: its checksum checked once,
then a `model-file` record); `POST /runtime/downloads`, `POST /runtime/model-files`; `clank model download MODEL
--format F [--role R] --host H [--yes] [--limit MB/s]`, `clank model adopt MODEL --format F [--role R] --host H --path
P`.

**Tests (a local web server serving a small file):** a download resumes from its `.part`; a wrong checksum is refused
and kept aside; a verified file is kept and a check passes.

### Task 4: This machine

**Steps (no code):** add the hosts (`Ubuntu-22.04`, `Ubuntu`); adopt KVMem's build and its two GGUF files; build NInfer

## Rulings made while building

- **Task 1: a recipe is its steps.** The plan listed a recipe's environment packages, source and verification as
  fields of their own; as built, the packages and the source are in the steps' commands (each step one command with
  what it makes), and the verification is the same for every recipe (the program's `--help` lists every flag its
  adapter can give). Fewer fields to keep consistent; if wrong, a field can be added when a second recipe needs it.
- **Task 1: half the cores, said by the recipe.** `{jobs}` is gone: a build step computes half the host's cores itself
  (`$(( ($(nproc) + 1) / 2 ))`) and runs at `nice -n 10`. If wrong, a recipe that forgets it builds on every core.
- **Task 1: `--host` is required.** No host suits every recipe as a default (`local` is Windows on this machine, where
  no recipe runs). One more word to type.
- **Task 1: the hosts run a step** (`run_step`, in the host contract, the WSL recording made again with a step): its
  output followed line by line, its exit status, and on cancel the command ended with what it started (in WSL, its
  process group). A WSL step's PATH leaves out Windows' folders: the spike's configure spent minutes searching them.
- **Task 1: v1.5's recipe waits** for v1.5's adapter version, which waits for a driver that runs CUDA 13.4 (decision
  0031 had both recipes side by side). Design 0003 §5 says so.
- **Task 1: dates are the owner's local dates.** M1.3's "done" date and decision 0032's had been written in UTC.
- **Task 2: the version of an adopted engine is its checkout's commit.** KVMem's server has no `--version` (it says
  "unknown flag"), so the adopt reads `git rev-parse HEAD` in the checkout it was built from and refuses another commit;
  a folder that is no checkout is refused, asking for its source. Local changes are not refused but recorded: the
  owner's KVMem checkout has some (its llama.cpp submodule, one script), and it is the engine they use every day. If
  wrong, a modified build passes as the version Clank knows; the install's detail says it was modified.
- **Task 2: `--folder` is required.** Where an engine runs cannot be read from its program's path (KVMem runs from its
  checkout's root, two folders above its program).
- **Task 3: the host's own Python fetches the file** (a script of the standard library, run as a step), so a model
  goes straight to the host's disk (WSL's own, not across the bridge from Windows), with no tool to install; every
  host has a Python (`PYTHON`: Clank's own here, `python3` in a distribution). The module is `modelfiles.py`, since
  `Runtime.models` is the catalog.
- **Task 3: one file per download** (`--role`, weights by default): the projector's revision is no longer known, so
  it is never downloaded, and a download of the model's files together would always fail on it.
- **Task 4: an install's tools get a home of their own.** The first install on this machine wrote outside the engine's
  folder: micromamba added a line to `~/.conda/environments.txt` and made `~/.mamba` and `~/.cache/mamba`, and CUDA
  wrote to its cache in `~/.nv` when the program was checked. Those additions were removed (CUDA's cache, shared with
  the owner's programs, was left), and a recipe now has an environment for every step and for the check of its program
  (`env`): NInfer's sets `HOME` in the engine's folder. A test holds every shipped recipe to it.
- **Task 3: no time is guessed before a download.** Design 0001 §7.5 asks for the time a download will take; nothing
  knows the network's speed before it starts, so the progress lines say the speed as it goes (design 0003 §7.2 says
  so). If wrong, a time can be estimated from the last download's speed.

## Final review

Self-review (no subagents), 2026-10-13, against the review focus: a download cut off halfway resumes and is used only
once verified (test_download); a checksum that differs is refused and kept aside (test_download); an adopted engine at
another commit, outside a checkout, or lacking a flag is refused saying what differs (test_adopt); a failing build
step stops the install with its last lines and the next install goes on from it (test_install); no leaves nothing
done (test_install, test_download). Found while doing task 4 and fixed, each with a test that failed first: Click
expanded `~` in arguments on Windows; an adopted engine's paths were not expanded on its host; the check asked
NInfer for a projector; a recipe's tools wrote into the user's home; an engine's last words could be missed when it
ended between two looks (M1.3's start check).

Deferred minors:
- An install interrupted by a restart of the service leaves its WSL step's process group running (its id is kept only
  in memory), and the next install would run that step beside it; a reconcile could end the group.
- An adopt reads every line `git status --porcelain` prints as a changed path, so a warning git writes there (an
  unsafe directory, say) would be recorded as one.
- A file the user adopted elsewhere can still be downloaded to the host's models folder; launches go on using the
  adopted one.
